1Executive summary

The Service Desk replaces informal, unrecorded handling of internal requests with one auditable workflow shared by every company in the group. Four operational registers — tickets, development requests, compliance obligations and management tasks — sit on a common foundation of organisational scope, role-based permissions, document numbering and audit logging.

Every record is tagged to a company and a location. A user only ever sees the companies and locations they have been granted, and within that, only what their role permits. Service levels are derived automatically from ticket priority and refreshed on a schedule, so breach reporting does not depend on anyone remembering to update a status.

The system is deployed and carrying live traffic. The organisational structure, user base and master data are fully loaded; transactional volume is still at pilot scale while the rollout proceeds company by company.

2Business context

Yousuf Dewan Companies operates twenty legal entities spanning cement, motors, textiles, sugar, spinning and trading, sharing a central IT function and common corporate services. Before this system, requests for IT support, software change and compliance follow-up moved by phone, email and walk-up. That created four recurring problems:

  • No record. Requests could not be counted, aged or attributed, so IT workload was invisible to management.
  • No accountability. Nothing recorded who owned a request or when it was due, and nothing escalated when it slipped.
  • No separation between entities. Group-wide staff worked across companies with no consistent rule for who could see which company's records.
  • No audit trail. Changes to requests, approvals and master data left no evidence, which internal audit and compliance both require.

The Service Desk addresses all four with a single application: recorded intake, assigned ownership with time-bound service levels, company and location scoping enforced at the query layer, and an immutable audit log of every create, update, approval and sign-in.

18Business rules

18.1 Document numbering

Numbers are human-readable and separate from the internal database key. Allocation runs inside a database package using an autonomous transaction, so concurrent requests serialise on the counter and the lock releases immediately without waiting for the surrounding business transaction. Counters restart per company, per document type, per year.

18.4 Transactional integrity

Every multi-table operation runs inside a single database transaction. Creating a ticket writes the ticket, its history row, the audit entry and the notifications together, or none of them. The same rule applies to assignment, status change, resolution, approval decisions and compliance updates.

Storage conventions

  • Long text — descriptions, resolutions, comments, findings, audit snapshots — is stored as character large objects.
  • Uploaded files are written to application storage; only the metadata and path are held in the database.
  • Audit change columns hold JSON validated by a database constraint.
  • Reporting views exist only where the logic is genuinely reusable; simple listings are built by query.

21Assumptions, dependencies and constraints

Assumptions

  • Every user has a unique email address or mobile number recorded in the HR roster.
  • One role per user is sufficient; a person needing two capability sets receives a role that combines them.
  • Service levels are measured in elapsed clock hours, not working hours.
  • Staff have a modern browser and network access to the internal site.

Dependencies

  • Oracle Database 19c with the SDESK schema in the ORCLPDB service — no other database engine is supported.
  • PHP 8.2 or later with the Oracle client extension enabled, and Oracle client libraries on the server path.
  • HTTPS with a valid certificate — browser push refuses to register otherwise.
  • A running task scheduler for SLA recalculation every fifteen minutes.
  • Master data — companies, locations, departments and users — must be loaded before a company can transact.

Constraints

  • Database credentials live in environment configuration and are never held in code.
  • Built-in role codes are fixed because the application matches on them.
  • The wildcard permission is reserved for the System Administrator role and cannot be granted through the interface.
  • Locations and departments are currently defined for Dewan Motors only; the other nineteen companies need theirs before rollout.
